# 08 — Architecture Decision Records (ADRs)

> This file is the permanent decision log. **Every future significant decision — not just the founding ones below — must be appended here**, never overwritten. **Amended during the Surfboard-alignment documentation pass** (see [09_PROMPT_HISTORY.md](09_PROMPT_HISTORY.md)): ADR-014/015/016 added, ADR-002/ADR-008 annotated to reflect the Surfboard-as-system-of-record decision — their original entries are kept intact per the "never edit history away" rule below, with a clarifying note on each. Related: [02_ARCHITECTURE.md](02_ARCHITECTURE.md), [20_DOMAIN_MODEL.md](20_DOMAIN_MODEL.md), [13_CLAUDE_CONTEXT.md](13_CLAUDE_CONTEXT.md).

**Format:** each entry has a Status, Context, Decision, Consequences, and Revisit trigger. Status is one of `Proposed`, `Accepted`, `Superseded by ADR-00X`, or `Accepted (amended)` — the last used when a decision is still substantially correct but a later ADR narrows/clarifies its scope without reversing it.

## ADR-001 — Why Flutter for the frontend

- **Status:** Accepted
- **Context:** SurfPOS AI must ship for both Android and iOS, mobile-first, with a UI-heavy feature set (scanner, camera capture) and a small initial engineering team.
- **Decision:** Use Flutter (Dart) as the single frontend codebase for Android and iOS.
- **Consequences:** One codebase instead of two native ones; strong first-party camera/barcode plugin ecosystem. Trade-off: Dart is a smaller hiring pool than JS/TS or Kotlin/Swift alone.
- **Revisit if:** the product needs deep native-only capability Flutter can't reach performantly, or a web/desktop client becomes priority.

## ADR-002 — Why Firebase (Auth, Realtime Database, Storage) for application data

- **Status:** Accepted (amended — see note below)
- **Context:** Target customers cannot manage servers, backups, or database administration.
- **Decision:** Use Firebase Authentication, Realtime Database, and Storage for **application data and identity** — no separate SQL/NoSQL database for that data.
- **Consequences:** Zero database-ops burden for application data; tight Firebase Auth ↔ RTDB Security Rules integration. Trade-off: RTDB has no complex/relational queries.
- **Amendment (2026-07-29, Surfboard-alignment pass):** The original wording of this ADR described Firebase as "the entire data platform" for SurfPOS AI. That is no longer accurate: Firebase is the data platform for **application data only** (inventory, catalog, sales, analytics, receipts, AI pipeline, settings — see [20_DOMAIN_MODEL.md § 1](20_DOMAIN_MODEL.md#1-the-ownership-principle)). Merchant, Store, Device, Payment, Branding, Tips, and Payment Methods are owned by Surfboard, not Firebase — see [ADR-014](#adr-014--surfboard-is-the-system-of-record-for-merchant-store-device-payment-branding-tips-and-payment-methods) below. Authentication and Storage remain fully accurate as originally decided; only the Realtime-Database-as-sole-datastore framing is narrowed.
- **Revisit if:** query complexity outgrows what denormalization can reasonably support, or RTDB throughput becomes a bottleneck.

## ADR-003 — Why Node.js + Express for the backend

- **Status:** Accepted
- **Context:** The backend's job is orchestration (Firebase Admin SDK, Gemini API, OCR, and now a much larger Surfboard integration surface) rather than heavy compute.
- **Decision:** Node.js + Express.js as a thin, stateless REST API layer, and — per this pass — the **sole gatekeeper** to both Firebase and Surfboard (see [02_ARCHITECTURE.md § 1](02_ARCHITECTURE.md#1-system-architecture-high-level)).
- **Consequences:** Naturally async, well suited to orchestrating multiple external calls per request. Trade-off: not ideal for CPU-heavy work.
- **Revisit if:** a CPU-bound workload needs to move in-process.

## ADR-004 — Why AI OCR + Gemini for invoice scanning

- **Status:** Accepted — unaffected by the Surfboard-alignment pass (the AI pipeline is entirely Firebase-owned data, see [20_DOMAIN_MODEL.md § 1](20_DOMAIN_MODEL.md#1-the-ownership-principle)).
- **Context/Decision/Consequences:** unchanged from the founding decision — see [16_AI_MODULE.md](16_AI_MODULE.md) for current detail.

## ADR-005 — Why smartphone-only POS (no dedicated terminal/hardware requirement)

- **Status:** Accepted
- **Context:** Dedicated POS hardware is a major upfront cost barrier for the target small-retailer customer.
- **Decision:** The phone's own camera is the barcode/invoice scanner; payment acceptance uses whichever Surfboard-supported method works from the phone or a Surfboard-linked device.
- **Consequences:** Zero-hardware onboarding. **Reinforced by this pass:** since Surfboard now owns Device identity outright (see [20_DOMAIN_MODEL.md § 2.3](20_DOMAIN_MODEL.md#23-device--surfboard-owned)), SurfPOS never needs its own device-management data layer — it's a straight proxy to Surfboard's Device API (see [19_SURFBOARD_WORKFLOWS.md § 3](19_SURFBOARD_WORKFLOWS.md#3-device-lifecycle)).
- **Revisit if:** optional hardware add-ons are prioritized.

## ADR-006 — Why cloud architecture (no local/offline-first-by-default design)

- **Status:** Accepted
- **Context/Decision:** unchanged — Firebase RTDB (application data) and Surfboard (its seven owned entities) are both cloud systems; the backend is stateless and cloud-hosted.
- **Consequences:** Checkout now genuinely requires connectivity to **two** external systems (Firebase for the Sale write, Surfboard for the Payment) — a stricter version of the original "checkout requires connectivity" constraint, not a new one.
- **Revisit if:** merchant feedback shows connectivity gaps are a frequent blocker at the point of sale.

## ADR-008 — Multi-tenant data model from day one, multi-store UI deferred

- **Status:** Accepted (amended — see note below)
- **Context:** Retrofitting a multi-tenant/multi-store schema after data exists is expensive and risky.
- **Decision:** Every Firebase application-data node is keyed/scoped by `merchantId` and, where relevant, `storeId`.
- **Amendment (2026-07-29, Surfboard-alignment pass):** `merchantId`/`storeId` are now **Surfboard-issued IDs** used as foreign-key references, not locally-generated Firebase push IDs as originally implied (Merchant/Store no longer have a Firebase-side record to generate an ID from at all — see [20_DOMAIN_MODEL.md § 1](20_DOMAIN_MODEL.md#1-the-ownership-principle)). The core decision (shape every application-data node for multi-tenancy from day one) is unchanged and still correct.
- **Revisit if:** never — this remains intentionally permanent.

## ADR-014 — Surfboard is the system of record for Merchant, Store, Device, Payment, Branding, Tips, and Payment Methods

- **Status:** Accepted
- **Context:** After researching the Surfboard Developer Portal and APIs, it became clear that Surfboard already models Merchant, Store, Device, Payment, Branding, Tips, and Payment Methods as first-class objects with their own lifecycle, status, and identity. The original plan (a `merchants`/`stores`/`payments` Firebase schema that separately recorded a `surfboardMerchantId` reference field) would have meant **two systems tracking the same business object**, guaranteed to drift out of sync (a stale cached `status`, a Firebase record surviving after the Surfboard side changes, etc.) — exactly the "disconnected payments and POS" problem SurfPOS AI exists to solve (see [01_PROJECT_OVERVIEW.md § 3](01_PROJECT_OVERVIEW.md#3-business-problem)), just moved one layer down.
- **Decision:** Surfboard is the sole system of record for Merchant, Store, Device, Payment, Branding, Tips, and Payment Methods. SurfPOS AI never persists a full copy of any of these in Firebase — it stores only the minimal ID reference needed to partition its own application data, and fetches everything else live through the Surfboard Integration Layer (see [20_DOMAIN_MODEL.md](20_DOMAIN_MODEL.md), [15_SURFBOARD_INTEGRATION.md](15_SURFBOARD_INTEGRATION.md)).
- **Consequences:** Impossible for SurfPOS's copy of a Merchant/Store/Payment to drift from Surfboard's, because there is no copy. Every screen that needs this data makes a live call (through the Integration Layer, with short-lived in-process caching where appropriate — never RTDB persistence). Trade-off: the backend now has a hard runtime dependency on Surfboard's availability/latency for a much larger share of its functionality than "just payments" — see [02_ARCHITECTURE.md § 9](02_ARCHITECTURE.md#9-scalability) for the resulting caching/timeout/circuit-breaking requirement this creates.
- **Impact:** Removes `merchants/{merchantId}`, `stores/{storeId}`, `payments/{paymentId}` from [03_DATABASE_DESIGN.md](03_DATABASE_DESIGN.md) entirely; rewrites [02_ARCHITECTURE.md](02_ARCHITECTURE.md), [04_API_DOCUMENTATION.md](04_API_DOCUMENTATION.md), [05_FEATURES.md](05_FEATURES.md), [15_SURFBOARD_INTEGRATION.md](15_SURFBOARD_INTEGRATION.md); amends [ADR-002](#adr-002--why-firebase-auth-realtime-database-storage-for-application-data)/[ADR-008](#adr-008--multi-tenant-data-model-from-day-one-multi-store-ui-deferred).
- **Revisit if:** Surfboard ever stops being the exclusive payments/merchant-identity integration (see [ADR-017](#adr-017--surfboard-payments-as-the-exclusive-payment-integration) for that separate, still-Accepted decision) — this ADR would need re-deriving from whatever replaces it.

## ADR-015 — Repository + Mapper pattern formalized

- **Status:** Accepted
- **Context:** [ADR-013](#adr-013--srcintegrations-vs-srcmodules-split) established that Firebase access and Surfboard access are separate layers, but didn't formalize the shape of the Firebase-access layer itself, or how wire-format translation happens on either side.
- **Decision:** Every Firebase-owned entity gets exactly one Repository (`<domain>.repository.js`) — the only code that calls the Firebase Admin SDK for that entity. Every Surfboard-owned entity's Integration Client is paired with a Mapper that translates Surfboard's wire format into the plain domain shapes defined in [20_DOMAIN_MODEL.md](20_DOMAIN_MODEL.md) (and Firebase records get a Mapper too, only where the raw shape needs translating). Full contract: [21_BACKEND_GUIDELINES.md §§ 4, 6](21_BACKEND_GUIDELINES.md#4-repository-firebase-owned-entities-only).
- **Consequences:** Services and Controllers never see a raw Firebase snapshot or raw Surfboard response body — only domain objects. A future Surfboard field-naming change is a one-file Mapper fix, not a hunt through every Service that touches that entity.
- **Revisit if:** never expected — this is a foundational code-organization decision, not a technology choice with an alternative to weigh.

## ADR-016 — Surfboard domain module split

- **Status:** Accepted
- **Context:** Earlier plans had one catch-all `modules/surfboard/` folder. With seven Surfboard-owned entities now formally distinguished ([ADR-014](#adr-014--surfboard-is-the-system-of-record-for-merchant-store-device-payment-branding-tips-and-payment-methods)), a single module would violate the same single-responsibility principle every other domain module follows.
- **Decision:** `modules/merchant/`, `modules/store/`, `modules/device/`, `modules/payments/`, `modules/branding/` each own one or more of the seven entities. **Payment Methods folds into `modules/store/`** (it's queried/configured as a capability of a Store, not a standalone lifecycle) and **Tips folds into `modules/payments/`** (tips are configured and collected as part of the payment flow) — neither gets its own module or its own Integration Client file, to avoid a five-entities-worth-of-ceremony for two capabilities with no independent lifecycle of their own.
- **Consequences:** Five focused modules instead of one broad one; two capabilities (Payment Methods, Tips) live inside the module of the entity they're most tightly coupled to, rather than each getting a same-weight module despite having far less surface area. See [19_SURFBOARD_WORKFLOWS.md](19_SURFBOARD_WORKFLOWS.md) for how each maps to its lifecycle, and [22_DEVELOPMENT_ROADMAP.md](22_DEVELOPMENT_ROADMAP.md) for how Payment Methods/Tips map onto the Phase 6/Phase 9 roadmap entries rather than getting their own phase number.
- **Revisit if:** Payment Methods or Tips ever grows an independent lifecycle (e.g. Surfboard exposes a standalone Tips API with its own onboarding/configuration flow unrelated to a single payment) — split it out into its own module/client at that point.

## ADR-017 — Surfboard Payments as the exclusive payment integration

- **Status:** Accepted
- **Context:** Surfboard Payments integration is a founding product requirement — SurfPOS AI is defined as "fully integrated with the Surfboard Payments ecosystem" (see [01_PROJECT_OVERVIEW.md](01_PROJECT_OVERVIEW.md)). This decision was recorded as `D-009` in `.claude/decision.md` at project founding but never given a formal entry in this file — added here now for completeness during the Surfboard-alignment pass.
- **Decision:** Surfboard Payments is the exclusive payment-processing integration for SurfPOS AI — all payment intents, merchant/store/device onboarding, and settlement flow through Surfboard's API, called only from the backend's Integration Layer.
- **Consequences:** Single payment relationship for the merchant — directly solves the disconnected-payments business problem in [01_PROJECT_OVERVIEW.md § 3](01_PROJECT_OVERVIEW.md#3-business-problem). Trade-off: single point of dependency on one payment provider; exact API surface still pending confirmation (see [ADR-009](#adr-009--pending-decisions-to-record-here-once-made)).
- **Impact:** `backend/src/integrations/surfboard/`, `backend/src/modules/{merchant,store,device,payments,branding}/`, [15_SURFBOARD_INTEGRATION.md](15_SURFBOARD_INTEGRATION.md), [19_SURFBOARD_WORKFLOWS.md](19_SURFBOARD_WORKFLOWS.md).
- **Revisit if:** a second payment provider is ever required (e.g. geographic expansion beyond what Surfboard supports).

## ADR-018 — Surfboard SDK implementation choices (Phase 2)

- **Status:** Accepted
- **Context:** Building the real HTTP plumbing behind `src/integrations/surfboard/` (Roadmap Phase 2, see [22_DEVELOPMENT_ROADMAP.md](22_DEVELOPMENT_ROADMAP.md)) required several concrete technical choices not dictated by prior ADRs: which HTTP client library, what retry/backoff shape, and how to handle two specifics of the Surfboard wire format that are still unconfirmed (auth header scheme, webhook signature scheme).
- **Decision:**
  1. **Native `fetch`** (global in Node ≥ 18, this project's minimum) is used for all Surfboard HTTP calls — no `axios`/`got`/`node-fetch` dependency added, since the runtime already provides everything needed (streaming not required, `AbortSignal` timeout support built in).
  2. **Retry:** exponential backoff (`200ms × 2^attempt`), default 2 retries, only for retryable conditions — HTTP 408/429/500/502/503/504 or a network-level error (`AbortError`, `ECONNRESET`, `ETIMEDOUT`). A 4xx other than 408/429 is never retried, since retrying a client-error response can't fix it.
  3. **Timeout:** `AbortController`-based, default 10 seconds, configurable per client instance via dependency injection (see [21_BACKEND_GUIDELINES.md § 12](21_BACKEND_GUIDELINES.md#12-dependency-injection)).
  4. **Auth header scheme** (`middleware/auth.middleware.js`) and **webhook signature scheme** (`utils/webhookSignatureVerifier.js`, HMAC-SHA256 over the raw payload) are both **explicit placeholders** — a reasonable, common convention chosen so the SDK is fully testable end to end, but neither is verified against Surfboard's actual documentation yet (tracked under [ADR-009](#adr-009--pending-decisions-to-record-here-once-made)). Both are isolated in one file each specifically so confirming the real scheme later is a one-file change, not a rewrite. **Auth scheme superseded by [ADR-019](#adr-019--surfboard-sdk-authentication-layer-strategy-pattern-extends-phase-2-not-roadmap-phase-3)**, which replaces the single hardcoded placeholder with a pluggable strategy abstraction (`middleware/auth.middleware.js` retired in favor of `middleware/authentication.middleware.js`); the webhook signature scheme remains a placeholder, unaffected by that pass.
- **Consequences:** Zero new runtime dependencies for the SDK; every domain client gets working retry/timeout/logging/error-mapping for free by inheriting `client/surfboardClient.base.js`, with no domain-specific code duplicating any of it. Trade-off: the auth and webhook-signature placeholders will need updating (and their existing unit tests adjusting) once real Surfboard credentials/docs are available — this is expected, tracked work, not a currently-known bug.
- **Impact:** `backend/src/integrations/surfboard/{client,middleware,models,mappers,utils,errors}/`, `backend/tests/integrations/surfboard/` (48 tests), `backend/src/constants/{httpStatus,errorCodes,messages}.js` (added `BAD_GATEWAY`/`SURFBOARD_ERROR`).
- **Revisit if:** Surfboard's confirmed API documentation specifies a different auth scheme, signature scheme, or retry/rate-limit contract than assumed here — update the isolated file, not the SDK's overall shape.

## ADR-019 — Surfboard SDK authentication layer: strategy pattern (extends Phase 2, not Roadmap Phase 3)

- **Status:** Accepted
- **Context:** Phase 2 ([ADR-018](#adr-018--surfboard-sdk-implementation-choices-phase-2)) deliberately left `middleware/auth.middleware.js` as a single-scheme placeholder (a hardcoded Bearer-style header built from `apiKey`) because Surfboard's real auth mechanism is still unconfirmed against official docs ([ADR-009](#adr-009--pending-decisions-to-record-here-once-made)). This work completes that deferred placeholder. **Naming clarification:** this is *not* [Roadmap Phase 3 — Client Authentication](22_DEVELOPMENT_ROADMAP.md#phase-3--client-authentication), which is Firebase Auth (merchant/staff sign-in) and remains untouched, `Not Started`, and still gated on explicit user approval per [13_CLAUDE_CONTEXT.md § 5](13_CLAUDE_CONTEXT.md). This ADR is scoped entirely to how the backend authenticates *to* Surfboard's API, inside `src/integrations/surfboard/`.
- **Decision:** Replace the single hardcoded auth placeholder with a strategy-pattern abstraction so the auth scheme is swappable without touching `SurfboardBaseClient` or any domain client:
  - `auth/authStrategy.js` — the `AuthStrategy` contract (`getAuthHeaders()`) and `STRATEGY_TYPES` (`api_key`/`bearer`/`oauth`).
  - `auth/strategies/{apiKeyStrategy,bearerTokenStrategy,oauthStrategy}.js` — one concrete strategy per scheme. `ApiKeyStrategy` preserves Phase 2's exact default behavior (Bearer-style header built from the static API key) so nothing regresses while the real scheme is still unconfirmed. `BearerTokenStrategy`/`OAuthStrategy` are token-based and each own a `provider/tokenProvider.js` (cache + refresh-skew logic in `provider/tokenRefreshStrategy.js`, storage in `cache/tokenCache.js` with single-flight refresh dedup).
  - `auth/authenticationManager.js` — resolves `SURFBOARD_AUTH_STRATEGY` to a strategy instance via an injectable factory map (constructor-injection per [21_BACKEND_GUIDELINES.md § 12](21_BACKEND_GUIDELINES.md#12-dependency-injection)); `auth/authConfig.js` validates the chosen strategy has the credentials it needs, fail-fast; `auth/credentialLoader.js` is the one place credentials are read out of config, with a `redact()` helper so a secret never reaches a log line unmasked.
  - `middleware/authentication.middleware.js` (`attachAuthentication()`) replaces the retired `middleware/auth.middleware.js` as the request pipeline's auth step; `SurfboardBaseClient` now awaits it and holds an injected/default `AuthenticationManager`.
  - `OAuthStrategy` deliberately does **not** route its token-endpoint call through `SurfboardBaseClient` — the token endpoint must not be authenticated with the token it's about to issue, and doing so would create a circular dependency between the auth layer and the request layer.
- **Consequences:** Swapping `SURFBOARD_AUTH_STRATEGY=api_key|bearer|oauth` (or registering an entirely new strategy) requires no SDK code changes. Existing Phase 2 behavior/tests are preserved by default (`api_key` strategy, no env changes required). Trade-off: `OAuthStrategy`'s token endpoint path/grant/response shape are still placeholders pending Surfboard's real OAuth docs — isolated to one file, same pattern as [ADR-018](#adr-018--surfboard-sdk-implementation-choices-phase-2).
- **Impact:** `backend/src/integrations/surfboard/{auth,provider,cache}/`, `backend/src/integrations/surfboard/middleware/authentication.middleware.js` (new), `middleware/auth.middleware.js` (retired), `client/{surfboardClient.base,surfboardConfig}.js`, `src/config/index.js` + `src/constants/environmentKeys.js` (+`SURFBOARD_AUTH_STRATEGY`/`SURFBOARD_BEARER_TOKEN`), `backend/.env.example`. 27 new unit tests.
- **Revisit if:** Surfboard's confirmed docs specify a different scheme than any of the three strategies here (add a new strategy file + factory entry, per the pattern) or a different token-endpoint contract for `OAuthStrategy` (update that one file only).

## ADR-020 — Application Client Authentication endpoint shape (Phase 3)

- **Status:** Accepted
- **Context:** [Roadmap Phase 3](22_DEVELOPMENT_ROADMAP.md#phase-3--client-authentication) is Firebase identity for SurfPOS's own users (merchant owners/staff) — distinct from [ADR-019](#adr-019--surfboard-sdk-authentication-layer-strategy-pattern-extends-phase-2-not-roadmap-phase-3)'s Surfboard SDK auth layer. [04_API_DOCUMENTATION.md § 2](04_API_DOCUMENTATION.md#2-auth--merchant-onboarding) already documents `POST /auth/register`, but that endpoint assumes the Firebase Auth account already exists client-side (`"Auth": "None (client passes the fresh ID token in the body for verification)"`) and orchestrates Surfboard Merchant + Store creation — that's Phase 4's job. This phase needed a way to create the Firebase account and app profile *before* any of that exists, with no Surfboard call at all.
- **Decision:**
  1. New, distinctly-named endpoints for this phase: `POST /auth/signup` (Firebase Admin SDK `createUser({email, password, displayName})` + `users/{uid}` profile write, default `role: "owner"`), `POST /auth/login` (verify a client-obtained Firebase ID token, return the matching profile — a thin, testable step above raw token verification), `GET /auth/me` (unchanged from existing docs), `POST /auth/logout` (`revokeRefreshTokens(uid)`). `POST /auth/register` is left exactly as documented, reserved for Phase 4.
  2. The backend owns account creation directly (`createUser`) rather than assuming a Flutter client already called Firebase's client SDK — there is no Flutter Firebase integration in this repo yet, so backend-owned signup is the only self-contained option available at this phase.
  3. `middleware/auth.middleware.js` (already scaffolded in Phase 1, explicitly called out as reused infrastructure in [22_DEVELOPMENT_ROADMAP.md](22_DEVELOPMENT_ROADMAP.md)'s Phase 3 description) was refactored into a DI factory (`createAuthMiddleware`) delegating token verification to `modules/auth/auth.service.js#verifyToken`, so there is exactly one Firebase ID token verification implementation shared with `POST /auth/login`, instead of two copies drifting apart. `req.user` keeps its original `{uid, email, phoneNumber}` shape — no per-request Firebase profile/role read was added (only `GET /auth/me` does that lookup), preserving the every-request performance characteristic Phase 1/2 already had.
  4. Route-level testing note: a `vi.mock('../src/firebase/admin.js', ...)` Supertest suite was attempted and did not intercept `auth.service.js`'s nested `require('../../firebase/admin')` call (same Vitest/CJS module-boundary class of issue as [ADR-018](#adr-018--surfboard-sdk-implementation-choices-phase-2)'s `instanceof` quirk). Resolved the same way: route-level tests assert deterministic wiring outcomes (validation errors, missing-auth-header 401s, and the "Firebase Admin SDK is not configured" boundary for well-formed requests) instead of mocking Firebase; full business-logic coverage (every success/error path of `signUp`/`login`/`getCurrentUser`/`logout`) lives in `auth.service.test.js` against constructor-injected fakes, per [21_BACKEND_GUIDELINES.md § 11](21_BACKEND_GUIDELINES.md#11-testing).
- **Consequences:** No contract conflict when Phase 4 implements the already-documented `POST /auth/register` — it remains free to keep its "no-auth, idToken-in-body, orchestrates Surfboard" shape untouched. `users/{uid}` profiles created in this phase carry only `{uid, email, displayName, role, status, createdAt, updatedAt}` — no `merchantId`/`storeIds` yet (per [03_DATABASE_DESIGN.md § 4.10](03_DATABASE_DESIGN.md#410-usersuid)'s full eventual shape); `users.repository.js` already exposes `update()` for Phase 4 to patch those in without a new repository. Trade-off: phone/OTP sign-in (also scoped to task 3.1 in [10_TASKS.md](10_TASKS.md)) is not implemented — email/password only, deferred.
- **Impact:** `backend/src/modules/auth/{auth.service,users.repository}.js`, `backend/src/validators/auth.validation.js`, `backend/src/controllers/auth.controller.js`, `backend/src/routes/auth.routes.js`, `backend/src/middleware/auth.middleware.js`, `backend/src/app.js`, `backend/src/constants/{apiRoutes,messages}.js`. 33 new tests.
- **Revisit if:** a Flutter Firebase client SDK integration is added later and signup moves client-side (this endpoint would then narrow to profile-provisioning only, matching `/auth/register`'s existing precondition shape) — or when phone/OTP sign-in is scoped.

## ADR-021 — Merchant application tracking entity (Phase 4)

- **Status:** Accepted
- **Context:** [Roadmap Phase 4](22_DEVELOPMENT_ROADMAP.md#phase-4--merchant-creation) was originally planned as `POST /auth/register` — one call orchestrating Firebase Auth + Surfboard Merchant creation + default Store creation + a `users/{uid}.merchantId`/`storeIds` write (see [19_SURFBOARD_WORKFLOWS.md § 1](19_SURFBOARD_WORKFLOWS.md#1-merchant-lifecycle), [ADR-020](#adr-020--application-client-authentication-endpoint-shape-phase-3)). This pass instead scoped Phase 4 narrowly to *creating and tracking a merchant application* only — explicitly no Store creation, no `users/{uid}` write — leaving the full-registration orchestration for later.
- **Decision:**
  1. New Firebase-owned entity, `merchantApplications/{uid}` (one per submitting user), distinct from the Surfboard-owned Merchant object itself — it tracks *the application*, not a duplicate of Merchant business fields, so it doesn't violate [20_DOMAIN_MODEL.md § 1](20_DOMAIN_MODEL.md#1-the-ownership-principle)'s ownership rule: `{ applicationId, merchantId (nullable until Surfboard assigns one), applicationStatus, applicationUrl (nullable), submittedAt, updatedAt }`.
  2. New endpoints `POST /merchant/applications`, `GET /merchant/applications/:id`, `GET /merchant/applications` — not `/auth/register`. One application per uid (a second `POST` while one exists is `409 CONFLICT`, no resubmission-after-rejection handling yet). `applicationId` defaults to the caller's `uid` when Surfboard's response doesn't provide a distinct application identifier (unconfirmed field, see [ADR-009](#adr-009--pending-decisions-to-record-here-once-made)) — since storage is already keyed by `uid`, this keeps `GET /:id` a simple ownership-scoped lookup (the repository is only ever read by the caller's own `uid`, so cross-user access is structurally impossible, not just checked) rather than needing a second `applicationId → uid` index.
  3. `merchant.client.js#createMerchant()` and a new `mappers/merchant.mapper.js` (`toWire`/`toDomain`, isolating Surfboard's still-unconfirmed field names) complete Phase 2's `merchant.client.js` placeholder.
  4. **Bug found and fixed:** `SurfboardBaseClient`'s constructor eagerly built an `AuthenticationManager` (which validates credentials, see [ADR-019](#adr-019--surfboard-sdk-authentication-layer-strategy-pattern-extends-phase-2-not-roadmap-phase-3)) — harmless while no controller's require chain ever reached `integrations/surfboard/`, but `merchantApplication.service.js` is the first to do so, and it crashed `app.js`'s module load entirely in any environment without `SURFBOARD_API_KEY` set (this project's test environment, and — more importantly — any real deployment before Surfboard credentials are provisioned, P.2). Fixed by making `authenticationManager` a lazy getter on `SurfboardBaseClient`, constructed on first access rather than in the constructor — the same lazy-init principle `firebase/admin.js` already uses. This is a bug fix to already-shipped SDK infrastructure, not new scope creep into Phase 2/ADR-019's territory.
  5. `merchantApplication.repository.js` takes its Firebase accessor as a DI parameter (`createMerchantApplicationRepository({ getDb })`), unlike `modules/auth/users.repository.js` (Phase 3), which calls `getDb()` directly with no injection seam. This is a deliberate inconsistency: the "Repository persistence" test requirement for this phase needs a real unit-test seam, and constructor injection is the only reliable option in this project's Vitest/CJS setup — `vi.mock()` on a nested `require('../../firebase/admin')` does not intercept (confirmed in [ADR-020](#adr-020--application-client-authentication-endpoint-shape-phase-3)). Retrofitting `users.repository.js` the same way would be a reasonable follow-up but is out of scope here (no bug there to fix, Phase 3 already shipped/approved).
  6. Route-level tests are wiring/validation smoke tests only (auth-before-validate ordering, 401s), for the same reason as [ADR-020](#adr-020--application-client-authentication-endpoint-shape-phase-3): default-wired Controllers reach real Firebase/Surfboard singletons, neither configured in this environment. Full business-logic coverage (submit/get/list, every success and mapped-error path including Surfboard-failure propagation) lives in `merchantApplication.service.test.js` against constructor-injected fakes.
- **Consequences:** `POST /auth/register` as originally documented remains unimplemented and is not superseded in shape — it's simply deferred; if it's still wanted later, it would need to additionally read/adopt an existing `merchantApplications/{uid}` record rather than assume a clean-slate orchestration. No Store is created and no `users/{uid}.merchantId` reference exists yet after this phase — anything gating on "does this user have a merchantId" must wait for that future work, not assume Phase 4 alone provides it.
- **Impact:** `backend/src/integrations/surfboard/{merchant.client.js,mappers/merchant.mapper.js}`, `backend/src/integrations/surfboard/client/surfboardClient.base.js` (bug fix), `backend/src/modules/merchant/{merchantApplication.service,merchantApplication.repository}.js`, `backend/src/validators/merchantApplication.validation.js`, `backend/src/controllers/merchantApplication.controller.js`, `backend/src/routes/merchantApplication.routes.js`, `backend/src/app.js`, `backend/src/constants/{apiRoutes,messages}.js`. 24 new tests (147 total backend-wide).
- **Revisit if:** Surfboard's confirmed docs specify a real `application_id` distinct from `merchant_id` (revisit the `applicationId` fallback and the single-`uid`-index lookup), or resubmission-after-rejection is scoped (revisit the always-409-if-exists rule).

## ADR-022 — Merchant Functions: merchantId resolution + repository composition (Phase 5)

- **Status:** Accepted
- **Context:** [Roadmap Phase 5](22_DEVELOPMENT_ROADMAP.md#phase-5--merchant-functions) needed live `GET`/`PATCH` merchant profile + status endpoints, scoped to the *authenticated caller's own* merchant — no `:merchantId` route param, matching the suggested `GET/PATCH /merchant`, `GET /merchant/status` shape. But per [ADR-021](#adr-021--merchant-application-tracking-entity-phase-4), Phase 4 deliberately never writes `users/{uid}.merchantId` — the only place a `merchantId` reference exists is the `merchantId` field already on `merchantApplications/{uid}` (nullable until Surfboard assigns one). Surfboard's docs also don't define a distinct "merchant status" endpoint.
- **Decision:**
  1. `merchant.service.js` resolves the caller's `merchantId` by reading their own `merchantApplications/{uid}` record (via a new `merchant.repository.js`) rather than a `users/{uid}.merchantId` field that doesn't exist yet. If no application exists, or one exists but no `merchantId` has been assigned (still pending KYC), all three endpoints return `404 NOT_FOUND` with a clear message rather than guessing or erroring opaquely.
  2. **`merchant.repository.js` does not call `getDb()` itself** — it composes `merchantApplication.repository.js` (`get`/`update`), since both would otherwise independently touch the exact same `merchantApplications/{uid}` node, violating "the only place a given Firebase-owned entity is read or written" ([21_BACKEND_GUIDELINES.md § 4](21_BACKEND_GUIDELINES.md#4-repository-firebase-owned-entities-only)). This still satisfies "create a MerchantRepository" as asked, while keeping a single real owner of the Firebase path.
  3. **No separate Surfboard "status" endpoint is assumed.** `GET /merchant/status` is implemented as a normalized view (`{ merchantId, status }`) built on top of the same `getMerchant()` call `GET /merchant` uses — per the explicit instruction not to invent an undocumented Surfboard endpoint. If Surfboard's real docs later reveal a distinct status endpoint, only `merchant.client.js#getMerchant()`'s call site inside `getMerchantStatus()` needs to change to call a new method.
  4. `merchant.client.js` gains `getMerchant(merchantId)` (`GET /merchants/:id`) and `updateMerchant(merchantId, wirePayload)` (`PATCH /merchants/:id`) — both unconfirmed wire-format guesses isolated the same way as `createMerchant()` ([ADR-018](#adr-018--surfboard-sdk-implementation-choices-phase-2), [ADR-021](#adr-021--merchant-application-tracking-entity-phase-4)). `merchant.mapper.js` gains `toMerchantProfile()`/`toMerchantUpdateWire()`, distinct from the existing `toDomain()`/`toWire()` (which normalize the narrower Merchant *Creation* shape, not the full profile).
  5. After every successful live `GET`/`PATCH`, the service refreshes only the already-tracked `applicationStatus` field on `merchantApplications/{uid}` (via `merchant.repository.js#cacheMerchantMetadata`) — never the full Merchant object, staying inside [20_DOMAIN_MODEL.md § 1](20_DOMAIN_MODEL.md#1-the-ownership-principle)'s ownership rule. This is the "if necessary, cache only minimal metadata locally" instruction, applied to the one field already being cached rather than a new one.
- **Consequences:** `GET/PATCH/status` all 404 for any user without an assigned `merchantId` yet (i.e., before Phase 4's application is approved) — expected given no linkage step exists yet. `merchant.repository.js` and `merchantApplication.repository.js` both live in `modules/merchant/`, so this composition is an in-module dependency, not a cross-module Repository reach (which [21_BACKEND_GUIDELINES.md § 8](21_BACKEND_GUIDELINES.md#8-cross-module-rule) forbids).
- **Impact:** `backend/src/integrations/surfboard/merchant.client.js` (+`getMerchant`/`updateMerchant`), `backend/src/integrations/surfboard/mappers/merchant.mapper.js` (+`toMerchantProfile`/`toMerchantUpdateWire`), `backend/src/modules/merchant/{merchant.service,merchant.repository}.js`, `backend/src/validators/merchant.validation.js`, `backend/src/controllers/merchant.controller.js`, `backend/src/routes/merchant.routes.js`, `backend/src/app.js`, `backend/src/constants/{apiRoutes,messages}.js`. 25 new tests (172 total backend-wide).
- **Revisit if:** Surfboard's confirmed docs define a real status endpoint (swap `getMerchantStatus()`'s internal call), or `users/{uid}.merchantId` linkage is later added (Phase 4's task 4.3 or equivalent) — at that point `merchantId` resolution could move there instead of `merchantApplications/{uid}`, though keeping it on the application record would still be harmless.

## ADR-023 — Store Capabilities: local registry + no invented list endpoint (Phase 6)

- **Status:** Accepted
- **Context:** [Roadmap Phase 6](22_DEVELOPMENT_ROADMAP.md#phase-6--store-capabilities) needed caller-scoped Store CRUD (`POST/GET /stores`, `GET/PATCH /stores/:storeId`), explicitly forbidding any invented/assumed Surfboard endpoint. Surfboard's docs don't confirm a "list stores by merchant" endpoint, yet `GET /stores` must still return every Store belonging to the caller's merchant. Like Phase 5, there is still no `users/{uid}.storeIds`/`merchantId` reference — `merchantId` must be resolved the same way Phase 5 solved it.
- **Decision:**
  1. **`GET /stores` is served from a local registry, not a live Surfboard list call.** `store.repository.js` owns a new node, `storeReferences/{uid}/{storeId}` — `{ storeId, merchantId, createdAt }`, written only when SurfPOS itself creates a Store via `POST /stores`. Listing reads this registry for the storeIds, then hydrates each with a live `getStore()` call — never persisting name/address/capabilities/status. This is the literal application of "if the Surfboard API is unavailable for a feature, create an interface, mark it a placeholder, document the assumption" applied to *listing* specifically, the same way [ADR-022](#adr-022--merchant-functions-merchantid-resolution--repository-composition-phase-5) applied it to *status*.
  2. **`GET`/`PATCH /stores/:storeId` authorize via registry membership** (`storeRepository.hasReference(uid, storeId)`) before ever calling Surfboard — a caller can only ever address a storeId their own registry lists, so this is ownership-safe by construction, not by trusting a live field to cross-check after the fact.
  3. **`merchantId` resolution reuses Phase 5's fix, but via a cross-module Service call, not Repository composition.** `store.service.js` calls `merchantService.getMerchantId(uid)` (a new export added to `modules/merchant/merchant.service.js`, wrapping its existing internal resolution logic) rather than reaching into `modules/merchant/merchant.repository.js` directly — because `modules/store/` and `modules/merchant/` are different modules, and [21_BACKEND_GUIDELINES.md § 8](21_BACKEND_GUIDELINES.md#8-cross-module-rule) forbids a Service calling another module's Repository directly (Service→Service is fine). This is different from `merchant.repository.js`'s own composition of `merchantApplication.repository.js` in Phase 5 — that was same-module, this is cross-module.
  4. `store.client.js` gains `createStore()`/`getStore()`/`updateStore()` (`POST`/`GET`/`PATCH /stores(/:id)`), all unconfirmed wire-format guesses isolated the same way as `merchant.client.js` ([ADR-018](#adr-018--surfboard-sdk-implementation-choices-phase-2), [ADR-021](#adr-021--merchant-application-tracking-entity-phase-4)). Deliberately **no** `listStoresByMerchant()` method — the file's own comment documents why, so nobody adds one assuming it's confirmed. `store.mapper.js` (`toWire`/`toDomain`/`toUpdateWire`) mirrors `merchant.mapper.js`'s shape.
- **Consequences:** `GET /stores` can only ever see Stores SurfPOS itself created — a Store created directly via Surfboard's own dashboard (outside SurfPOS) would not appear, a known and documented limitation of not having a confirmed list endpoint. `POST /stores` requires a resolved `merchantId` (404 otherwise, same as Phase 5). Multiple stores per merchant are already supported (no artificial single-store limit was added) — see the re-scoped task 6.3 in [10_TASKS.md](10_TASKS.md).
- **Impact:** `backend/src/integrations/surfboard/store.client.js`, `backend/src/integrations/surfboard/mappers/store.mapper.js`, `backend/src/modules/store/{store.service,store.repository}.js`, `backend/src/modules/merchant/merchant.service.js` (+`getMerchantId` export), `backend/src/validators/store.validation.js`, `backend/src/controllers/store.controller.js`, `backend/src/routes/store.routes.js`, `backend/src/app.js`, `backend/src/constants/{apiRoutes,messages}.js`. 29 new tests (201 total backend-wide).
- **Revisit if:** Surfboard's confirmed docs reveal a real list-stores-by-merchant endpoint (swap `listStores()`'s internal implementation to call it instead of hydrating the local registry — the registry could then become purely advisory or be dropped), or `users/{uid}.storeIds` linkage is added later (Phase 4 task 4.3 or equivalent).

## ADR-024 — Inventory Management: in-memory search + transactional stock (Phase 7)

- **Status:** Accepted
- **Context:** [Roadmap Phase 7](22_DEVELOPMENT_ROADMAP.md#phase-7--inventory) needed Product catalog CRUD (with search/filter/pagination/soft-delete) and per-store stock adjustment — entirely Firebase-owned, no Surfboard call at all. `products/{merchantId}/{productId}` and `inventory/{storeId}/{productId}` were already documented (pre-dating this implementation pass) in [03_DATABASE_DESIGN.md §§ 4.1–4.2](03_DATABASE_DESIGN.md#41-productsmerchantidproductid)/[20_DOMAIN_MODEL.md §§ 2.8–2.9](20_DOMAIN_MODEL.md#28-inventory--firebase-owned), but neither had an implementation yet, and Realtime Database has no native full-text search or range-query pagination as convenient as Firestore's.
- **Decision:**
  1. **One `modules/inventory/` module, two Repositories, one Service** — `product.repository.js` (owns `products/{merchantId}/{productId}`) and `stock.repository.js` (owns `inventory/{storeId}/{productId}`) are separate files per [21_BACKEND_GUIDELINES.md § 4](21_BACKEND_GUIDELINES.md#4-repository-firebase-owned-entities-only)'s one-entity-per-repository rule, but `inventory.service.js` is the single `InventoryService` the brief asked for, composing both (same-module composition, not cross-module).
  2. **Search/filter/pagination are done in-memory**, not via RTDB range queries: `product.repository.js#list()` reads the merchant's full product list once, then filters (search substring on `name`, exact `category`/`barcode`, `isActive`) and paginates (stable `id`-ordered cursor) in JS. This is a deliberate simplification appropriate for the target small-retailer catalog size ([01_PROJECT_OVERVIEW.md](01_PROJECT_OVERVIEW.md)) — proper indexing (or a move to Firestore/Algolia-style search) would be needed if catalog sizes grow much larger.
  3. **Stock adjustment is transactional and upserts on first restock.** `stock.repository.js#adjustQuantity()` extends the worked transaction example already in [21_BACKEND_GUIDELINES.md § 4](21_BACKEND_GUIDELINES.md#4-repository-firebase-owned-entities-only): if no record exists yet and the delta is positive, it creates one; if the delta would take quantity negative (whether reducing an existing record or reducing one that doesn't exist), the transaction aborts and the Service throws a new `InsufficientStockError` (`utils/errors.js`, `422`) — this was anticipated but not yet implemented ([07_CODING_RULES.md § 7](07_CODING_RULES.md#7-error-handling)'s "a future `InsufficientStockError`").
  4. **Barcode lookup (task 7.3) folded into `GET /inventory/products?barcode=`** rather than a separate endpoint — the suggested endpoint list for this phase didn't include one, and the existing `barcode` filter already serves it.
  5. **Cross-module ownership resolution reuses Phase 5/6's exports**, not Repository reach-through: `inventory.service.js` calls `merchantService.getMerchantId(uid)` for the product catalog's `merchantId`, and `storeService.verifyStoreOwnership(uid, storeId)` before any stock adjustment — both per [21_BACKEND_GUIDELINES.md § 8](21_BACKEND_GUIDELINES.md#8-cross-module-rule).
  6. **`supplierId` added as a new optional field on Product** (referencing the already-documented but not-yet-built Supplier entity, [20_DOMAIN_MODEL.md § 2.16](20_DOMAIN_MODEL.md#216-supplier--firebase-owned-new-in-this-pass)) — Supplier's own CRUD (task 7.4) is explicitly **not** built this pass; only the reference field exists so a product can carry it once Supplier CRUD lands.
- **Consequences:** `GET /inventory/products` reads the merchant's entire catalog on every call (bounded by realistic small-retailer catalog sizes, not paginated at the database layer) — acceptable now, a known scaling limit to revisit later. Stock quantity can never go negative by construction, regardless of which caller (this manual endpoint, or a future Billing checkout) requests the deduction.
- **Impact:** `backend/src/modules/inventory/{inventory.service,product.repository,stock.repository}.js`, `backend/src/validators/inventory.validation.js`, `backend/src/controllers/inventory.controller.js`, `backend/src/routes/inventory.routes.js`, `backend/src/utils/errors.js` (+`InsufficientStockError`), `backend/src/modules/store/store.service.js` (+`verifyStoreOwnership` export), `backend/src/app.js`, `backend/src/constants/messages.js`. 32 new tests (233 total backend-wide).
- **Revisit if:** catalog sizes outgrow in-memory filtering (add real indexing/dedicated search), or Billing (Phase 8) needs `adjustStock` for checkout — it can reuse this same transactional path.

## ADR-025 — Firebase infrastructure connection: real credentials, modular API migration, test/prod isolation

- **Status:** Accepted
- **Context:** P.1 (Firebase project setup) had been an open prerequisite since Phase 1 — all backend Firebase code (`firebase/admin.js`, every Repository) was written and tested against fakes/DI, never a real project. The user provided a real service-account key for project `surfpos-ai`, surfacing three latent issues invisible until real credentials existed.
- **Decision:**
  1. **Per-service config validation.** `firebase/admin.js#hasIdentity()` (projectId/clientEmail/privateKey) gates `initializeApp()`; `getDb()`/`getStorageBucket()` each additionally require their own `FIREBASE_DATABASE_URL`/`FIREBASE_STORAGE_BUCKET` (new env var) and throw a specific, actionable error if missing — replacing one all-or-nothing `isConfigured()` gate that blocked Auth on RTDB/Storage being configured too.
  2. **`firebase-admin` v13+ modular API.** `admin.credential.cert()` and `app.auth()`/`app.database()`/`app.storage()` — the shape this code was originally written against — don't exist in the installed `firebase-admin@^14.2.0`. Fixed to `admin.cert()` plus `getAuth(app)`/`getDatabase(app)`/`getStorage(app)` from `firebase-admin/{auth,database,storage}`. This is a bug fix to Phase 1 infrastructure (silently broken since whenever the dependency was pinned to v14), not new scope.
  3. **Test credentials must never load.** `config/index.js` now loads `.env.test` (not `.env`) whenever `NODE_ENV=test` — Vitest sets this before config loads. `.env.test` doesn't exist, so dotenv no-ops and every credential stays unset, preserving every existing "Firebase unconfigured in this environment" test assumption ([ADR-020](#adr-020--application-client-authentication-endpoint-shape-phase-3)/[ADR-021](#adr-021--merchant-application-tracking-entity-phase-4)) — this was previously *unenforced*, and one test run before this fix created a real user in the live project (found and deleted).
  4. **`.gitignore` fix.** The service-account pattern didn't match Firebase Console's actual filename shape; broadened to `*firebase-adminsdk*.json`, plus added `google-services.json`/`GoogleService-Info.plist`.
  5. **Frontend gets only `firebase_auth`, not `firebase_database`/`firebase_storage`** — the Flutter app never talks to RTDB/Storage directly ([02_ARCHITECTURE.md § 2](02_ARCHITECTURE.md)), so those packages have no legitimate use client-side. `main.dart` calls bare `Firebase.initializeApp()` (no generated `firebase_options.dart`/`FirebaseOptions`), relying on the platform-native `google-services.json`/`GoogleService-Info.plist` — neither exists in this repo yet, so the Android build fails at the `google-services` Gradle plugin step with a clear "file is missing" error (verified live), not a vague failure.
- **Consequences:** Auth and Realtime Database are both genuinely connected and verified (backend `listUsers()` and a real RTDB read/write round-trip both succeed against the real project; `npm run verify:firebase` reports it). Storage was explicitly deferred by the user rather than left as an unresolved gap — `FIREBASE_STORAGE_BUCKET` stays unset until a feature actually needs Storage (Receipts/AI invoice images); no value was guessed or invented for it. The Android build cannot succeed until a real `google-services.json` is added to `android/app/`.
- **Impact:** `backend/src/firebase/admin.js`, `backend/src/config/index.js`, `backend/src/constants/environmentKeys.js`, `backend/.env`/`.env.example`, `backend/scripts/verifyFirebaseConnection.js`, `backend/package.json` (+`verify:firebase`), `.gitignore`, `frontend/pubspec.yaml`, `frontend/lib/main.dart`, `frontend/android/{settings.gradle.kts,app/build.gradle.kts}`.
- **Revisit if:** Storage is needed by a future feature (provide `FIREBASE_STORAGE_BUCKET`, re-run `verify:firebase` to confirm) or a real `google-services.json`/`GoogleService-Info.plist` is provided (re-run the Android/iOS build).
