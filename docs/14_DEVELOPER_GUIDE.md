## 3. Flutter Setup

```bash
cd mobile
flutter pub get
flutter doctor         # confirm no blocking issues
```

- Configure Firebase for Flutter using `flutterfire configure` (generates `firebase_options.dart` — this file is safe to commit; it contains client-side config identifiers, not secrets).
- Run on a connected device/emulator:
  ```bash
  flutter run
  ```
- Run tests:
  ```bash
  flutter test
  ```
- Analyze/lint:
  ```bash
  flutter analyze
  ```

## 4. Node Setup

```bash
cd backend
npm install
```

- Copy the example environment file and fill in real values:
  ```bash
  cp .env.example .env
  ```

- Run in development (with hot reload, e.g. via `nodemon`):
  ```bash
  npm run dev
  ```
- Run in production mode:
  ```bash

  ```
- Run tests / lint:
  ```bash

  ```

## 5. Firebase Setup

**Firebase holds application data and identity only** — inventory, catalog, sales, analytics, receipts, AI pipeline data, and Firebase Auth. It does **not** hold Merchant, Store, Device, Payment, Branding, Tips, or Payment Methods data — those come from Surfboard (§ 5a) via the backend's Integration Layer. See [20_DOMAIN_MODEL.md § 1](20_DOMAIN_MODEL.md#1-the-ownership-principle).

1. Create a Firebase project in the Firebase Console.
2. Enable **Authentication** → Email/Password and Phone providers.
3. Create a **Realtime Database** instance (choose a region close to the primary user base).
4. Enable **Storage**.
5. Generate a **service account key** (Project Settings → Service Accounts) for backend use — **never commit this file**; load it via environment variables (see § 6).
6. Deploy security rules from the repo (once `database.rules.json` exists per [03_DATABASE_DESIGN.md § 8](03_DATABASE_DESIGN.md#8-security-rules-summary)):
   ```bash
   firebase deploy --only database
   ```

## 5a. Surfboard Setup

1. Obtain sandbox/developer credentials from the Surfboard Developer Portal (`SURFBOARD_API_KEY`/`SURFBOARD_API_SECRET`/`SURFBOARD_WEBHOOK_SECRET`, see § 6).
2. Confirm the official Surfboard API documentation for Merchant/Store/Device/Payment/Branding/Tips/Payment Methods endpoints — [15_SURFBOARD_INTEGRATION.md](15_SURFBOARD_INTEGRATION.md) describes the integration pattern, not verified wire format, until this step is done.
3. No Firebase rules or config are needed for Surfboard-owned data — there is nothing to deploy on the Firebase side for it.

## 6. Environment Variables

Backend (`backend/.env`, never committed — `.env.example` **is** committed as a template with placeholder values):

```env
# Server
PORT=4000
NODE_ENV=development

# Firebase Admin
FIREBASE_PROJECT_ID=surfpos-ai
FIREBASE_CLIENT_EMAIL=firebase-adminsdk-xxxx@surfpos-ai.iam.gserviceaccount.com
FIREBASE_PRIVATE_KEY="-----BEGIN PRIVATE KEY-----\n...\n-----END PRIVATE KEY-----\n"
FIREBASE_DATABASE_URL=https://surfpos-ai-default-rtdb.firebaseio.com

# AI
GEMINI_API_KEY=your-gemini-api-key
OCR_PROVIDER_API_KEY=your-ocr-provider-key   # if using a cloud OCR provider — see 16_AI_MODULE.md

# Surfboard Payments
SURFBOARD_API_KEY=your-surfboard-api-key
SURFBOARD_API_SECRET=your-surfboard-api-secret
SURFBOARD_WEBHOOK_SECRET=your-surfboard-webhook-signing-secret
SURFBOARD_ENV=sandbox   # sandbox | production
```

Frontend (`frontend/`): no secrets are stored client-side. Firebase client config comes from `firebase_options.dart` (generated by `flutterfire configure`, safe to commit — it's a public client identifier, not a secret). The backend base URL is never hardcoded — see [23_ENVIRONMENT_CONFIGURATION.md](23_ENVIRONMENT_CONFIGURATION.md) for the full picture (development uses `frontend/.env`, copied from `frontend/.env.example`; staging/production use `--dart-define`).

## 7. Running Backend + Frontend Together (Local Development)

1. Start the backend: `cd backend && npm run dev` (default `http://localhost:4000`).
2. One-time only: `cd frontend && cp .env.example .env`, then set `API_BASE_URL` — `http://10.0.2.2:4000` for the Android emulator, `http://localhost:4000` for the iOS simulator, or your machine's current LAN IP for a physical device. See [23_ENVIRONMENT_CONFIGURATION.md § 4](23_ENVIRONMENT_CONFIGURATION.md#4-development-workflow-the-wi-fi-switching-case) — this is also what to update whenever you switch Wi-Fi networks.
3. Run the Flutter app: `cd frontend && flutter run`.
4. Both the Flutter app (via Firebase SDKs) and the backend (via Firebase Admin SDK) talk to the **same** Firebase project — use a dedicated **development** Firebase project, never the production project, for local work.

## 8. Deployment

_Exact deployment target (e.g. Cloud Run, a container platform, or a serverless functions approach) is to be finalized and logged as an ADR in [08_ARCHITECTURE_DECISIONS.md](08_ARCHITECTURE_DECISIONS.md) before Phase 1 ships._ General shape:

- **Backend:** containerized Node/Express app, deployed to any Node-compatible host (e.g. Cloud Run, a managed container service). Stateless, so horizontal scaling is just "run more instances" (see [02_ARCHITECTURE.md § 10](02_ARCHITECTURE.md#10-scalability)).
- **Firebase:** Security Rules and any indexes are deployed via `firebase deploy --only database`. Keep a separate Firebase project per environment (`dev`, `staging`, `production`).
- **Mobile:** standard Flutter release builds —
  ```bash
  flutter build apk --release --dart-define=API_BASE_URL=https://api.surfpos.ai/api/v1
  flutter build ipa --release --dart-define=API_BASE_URL=https://api.surfpos.ai/api/v1
  ```
  distributed via Play Console / App Store Connect (or an internal track first).
- **Environment separation:** never point a release build at the `dev` Firebase project or Surfboard sandbox credentials — confirm build-flavor-to-environment mapping before every release.

## 9. Debugging

- **Flutter:** use `flutter run` with hot reload for UI iteration; Flutter DevTools for widget-tree/inspector and performance profiling; check [07_CODING_RULES.md § 12](07_CODING_RULES.md#12-performance) before assuming a rebuild-storm is "just how Flutter is."
- **Backend:** structured logs (see [07_CODING_RULES.md § 9](07_CODING_RULES.md#9-logging)) include a `requestId` — use it to trace a single request across log lines. Run `npm run dev` with a debugger attached (`node --inspect`) for step-through debugging.
- **Firebase data issues:** use the Firebase Console's Realtime Database viewer to inspect the actual tree shape against [03_DATABASE_DESIGN.md](03_DATABASE_DESIGN.md) — a mismatch there is a fast way to spot a bug before it's a symptom in the app.
- **Payment issues:** check Surfboard's sandbox dashboard/logs (once integrated) alongside the backend's webhook logs and the referencing Sale's `surfboardPaymentId`/`paymentStatus` fields — there is no Firebase `payments` node to inspect (see [03_DATABASE_DESIGN.md § 1](03_DATABASE_DESIGN.md#1-scope-of-this-schema)); the full Payment object is only ever visible via a live `GET /payments/:paymentId` call or Surfboard's own dashboard.
- **Merchant/Store/Device/Branding issues:** these have no Firebase representation to inspect at all — check the relevant Integration Client's logged request/response (IDs only, never full bodies — see [21_BACKEND_GUIDELINES.md § 10](21_BACKEND_GUIDELINES.md#10-logging)) and Surfboard's own dashboard.
- **AI extraction issues:** inspect the `invoiceScans/{merchantId}/{scanId}` record directly (raw OCR text + Gemini output are both stored) to tell whether OCR or Gemini structuring is the failure point — see [16_AI_MODULE.md § Error Handling](16_AI_MODULE.md#6-error-handling).
