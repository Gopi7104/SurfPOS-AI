### Feature-folder rationale

Each feature under `lib/features/<name>/` is self-contained, and **will be** internally organized (once implementation begins — not scaffolded up front) as:
- `data/` — models (DTOs) and repositories (talk to Firebase SDKs or the backend `ApiClient`).
- `domain/` — entities and use-case classes containing the actual business rules for that feature (kept out of widgets — see [07_CODING_RULES.md § 14](07_CODING_RULES.md#14-keep-business-logic-out-of-the-ui)).
- `presentation/` — screens, feature-local widgets, and Riverpod providers wiring `domain` to the UI.

This maps directly to the feature list in [05_FEATURES.md](05_FEATURES.md) — one folder per numbered feature section there (`merchant/` ↔ § 1, `authentication/`/`profile/` ↔ § 2, etc.).

## 3. `backend/` (Node.js + Express) — Full Tree

```
backend/
├── src/
│   ├── config/                 # Env loading/validation, third-party client config
│   ├── routes/                 # Express route definitions — thin, no logic
│   ├── controllers/            # Request-in/response-out only — see 07_CODING_RULES.md § 4
│   ├── middleware/
│   │   # auth.middleware.js · validate.middleware.js · rateLimit.middleware.js · error.middleware.js
│   ├── services/               # Shared/cross-cutting service logic
│   │
│   ├── modules/                 # Domain-specific service modules
│   │   ├── auth/                # See 05_FEATURES.md § 2
│   │   ├── merchant/            # See 05_FEATURES.md § 1
│   │   ├── inventory/           # THE only place inventory is mutated — see 07_CODING_RULES.md § 8
│   │   ├── billing/             # THE only place sale totals are computed
│   │   ├── payments/            # Payment records + webhook reconciliation
│   │   ├── receipts/            # Receipt generation
│   │   ├── analytics/           # Rollup aggregation + insights retrieval
│   │   ├── ai/                  # OCR, Gemini structuring/insights, product matching — see 16_AI_MODULE.md
│   │   └── surfboard/           # All Surfboard Payments API calls — see 15_SURFBOARD_INTEGRATION.md
│   │
│   ├── firebase/                # Firebase Admin SDK init + RTDB/Storage helpers
│   ├── utils/                   # Cross-cutting helpers, incl. the single logger instance
│   ├── constants/                # Shared constants/enums, kept in sync with 03_DATABASE_DESIGN.md § 6
│   ├── validators/               # Request validation schemas, one per resource
│   ├── logs/                     # Local dev log output (gitignored)
│   ├── docs/                     # Generated/OpenAPI API docs (distinct from top-level /docs)
│   ├── app.js                    # Express app instance — testable without a port
│   └── server.js                 # Boots app.js and binds a port
│
├── tests/                        # Mirrors src/ — see 18_CONTRIBUTING.md § 5
├── package.json
└── .env.example                  # Template — see 14_DEVELOPER_GUIDE.md § 6
```

### Layer rationale

`routes → controllers → services/modules → (Firebase Admin SDK / external APIs)` — strictly one direction. A controller never calls Firebase directly; a route never contains logic. This is the enforceable shape behind [07_CODING_RULES.md § 3](07_CODING_RULES.md#3-folder-conventions).

## 5. Where New Things Go (Quick Reference)

| Adding... | Goes in |
|---|---|
| A new Flutter screen for an existing feature | `frontend/lib/features/<feature>/presentation/` |
| A new Flutter feature entirely | New `frontend/lib/features/<name>/` following the `data/domain/presentation` shape |
| A new shared UI component (used by 2+ features) | `frontend/lib/core/widgets/` |
| A new backend REST resource | New `routes/`, `controllers/`, and a service under the relevant `modules/<name>/` (or `services/` if cross-cutting), plus a `validators/` schema — all together, not a subset |
| A new AI capability | `backend/src/modules/ai/` |
| A new Firebase schema node/field | Document it in [03_DATABASE_DESIGN.md](03_DATABASE_DESIGN.md) **before** writing the code that uses it |
| A new third-party integration | Its own module under `backend/src/modules/`, never called directly from a controller |
| A new Firebase Security Rule | `firebase/database.rules.json` or `firebase/storage.rules` — version-controlled, never console-only edits |
