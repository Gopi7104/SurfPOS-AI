### Feature-folder rationale

Each feature under `lib/features/<name>/` is self-contained:
- `data/` — models (DTOs) and repositories (talk to Firebase SDKs or the backend `ApiClient`).
- `domain/` — entities and use-case classes containing the actual business rules for that feature (kept out of widgets — see [07_CODING_RULES.md § 14](07_CODING_RULES.md#14-keep-business-logic-out-of-the-ui)).
- `presentation/` — screens, feature-local widgets, and Riverpod providers wiring `domain` to the UI.

This maps directly to the feature list in [05_FEATURES.md](05_FEATURES.md) — one folder per numbered feature section there.

### Layer rationale

`routes → controllers → services → (Firebase Admin SDK / external APIs)` — strictly one direction. A controller never calls Firebase directly; a route never contains logic. This is the enforceable shape behind [07_CODING_RULES.md § 3](07_CODING_RULES.md#3-folder-conventions).

## 4. Where New Things Go (Quick Reference)

| Adding... | Goes in |
|---|---|
| A new Flutter screen for an existing feature | `mobile/lib/features/<feature>/presentation/` |
| A new Flutter feature entirely | New `mobile/lib/features/<name>/` following the `data/domain/presentation` shape |
| A new shared UI component (used by 2+ features) | `mobile/lib/shared/widgets/` |
| A new backend REST resource | New `routes/`, `controllers/`, `services/`, `validations/` file for that resource — all four, not a subset |
| A new AI capability | `backend/src/services/ai/` |
| A new Firebase schema node/field | Document it in [03_DATABASE_DESIGN.md](03_DATABASE_DESIGN.md) **before** writing the code that uses it |
| A new third-party integration | Its own `*.service.js` under `backend/src/services/`, never called directly from a controller |
