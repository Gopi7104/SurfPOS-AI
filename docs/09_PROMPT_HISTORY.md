- **Reason:** Phase 2 ([ADR-018](08_ARCHITECTURE_DECISIONS.md#adr-018--surfboard-sdk-implementation-choices-phase-2)) deliberately left the auth-header attachment as a single hardcoded placeholder pending confirmed Surfboard docs. Building the *abstraction* now (rather than waiting for real credentials) is possible and valuable because the strategy pattern isolates the still-unconfirmed wire-level specifics to one small file per scheme — exactly the same "isolate the guesswork" approach ADR-018 already used for the webhook signature scheme.
- **Decision:** Before writing any code, cross-checked the user's "Phase 3" framing against `docs/10_TASKS.md`/`docs/22_DEVELOPMENT_ROADMAP.md`, which define the roadmap's actual Phase 3 as **Firebase Auth (merchant/staff sign-in)** — a different, unrelated piece of work that [13_CLAUDE_CONTEXT.md § 5](13_CLAUDE_CONTEXT.md) explicitly gates on user approval and which remains `Not Started`, untouched. Rather than blocking on this naming mismatch, proceeded with the (well-specified, clearly-scoped) Surfboard SDK auth work and recorded it as [ADR-019](08_ARCHITECTURE_DECISIONS.md#adr-019--surfboard-sdk-authentication-layer-strategy-pattern-extends-phase-2-not-roadmap-phase-3) — extending Phase 2, explicitly *not* claiming the roadmap's Phase 3 number, so the two are never conflated in the living docs. Default strategy (`api_key`) reproduces Phase 2's exact prior behavior so no regression occurs for existing callers/tests. `OAuthStrategy` fetches its own token directly (injectable `fetchImpl`, not routed through `SurfboardBaseClient`) to avoid a circular dependency between the auth layer and the request layer it feeds. One test needed adjusting for the same Vitest CJS/ESM module-boundary `instanceof` quirk already documented in the Phase 2 entry below — fixed by asserting on the thrown error's message instead, consistent with that established pattern.

No file under `modules/`, `controllers/`, `routes/`, or `firebase/` was touched — confirmed via `git status` before finishing.

[ADR-002](08_ARCHITECTURE_DECISIONS.md#adr-002--why-firebase-auth-realtime-database-storage-for-application-data) and [ADR-008](08_ARCHITECTURE_DECISIONS.md#adr-008--multi-tenant-data-model-from-day-one-multi-store-ui-deferred) were amended in place (not deleted) with a note narrowing their scope, per this file's own "never edit history away" rule.
